> 作者：Business Analyst (BMad Method v6)

## 1. Executive Summary

校园食堂智能推荐系统是一个面向高校食堂场景的"点餐 + 智能推荐 + 数据分析"一体化 Web 平台，服务学生、窗口管理员与系统管理员三类角色。系统通过多策略推荐引擎（协同过滤 / 内容 / 上下文 / 热门）+ 健康目标推荐，结合订单—评价—积分商城的完整业务闭环和管理侧的数据分析看板，把传统"排队点餐"升级为"千人千面的个性化点餐体验"。区别于普通的食堂点餐 SaaS，本系统的核心差异是**可解释、多策略融合的智能推荐**和**面向运营决策的高级数据分析能力**。

---

## 2. Problem Statement

高校食堂场景下，传统点餐流程与运营方式存在三类问题：

1. **学生选餐困难**：食堂菜品多、组合杂、口味偏好差异大，学生每天在"今天吃什么"上消耗决策成本，且很难根据自身饮食习惯（健康目标、口味偏好、季节天气）做出合适的选择。
2. **窗口与管理方运营盲目**：传统食堂依靠经验排菜、定促销，缺乏对销量趋势、用户分群、关联购买、差评信号等数据的实时观测，导致选品、促销和服务改进效率低。
3. **学生反馈链路断裂**：传统食堂没有结构化评价 → 关键词分析 → 警示响应的闭环，学生差评得不到及时回应、积极反馈得不到激励。

### Why Now
- 高校信息化建设深入，校园一卡通、微信支付等基础设施已经普及。
- 推荐算法、文本挖掘、可视化分析在中小规模业务系统上的工程实现门槛大幅降低（Spring Boot + Redis 即可承载）。
- 大学生群体对"个性化、健康化饮食"的关注度持续上升。

### Impact If Unsolved
- 学生：体验差、选餐效率低、健康饮食目标难落地。
- 窗口/食堂：经营依靠拍脑袋，热门菜断货 / 冷门菜浪费同时发生。
- 学校管理：缺乏对食堂服务质量的数据化抓手。

## 3. Target Audience

### 3.1 Primary Users（高频日常使用）

**学生（STUDENT）**
- 在校本科生 / 研究生，主力 18–25 岁
- 技术熟练度高（移动互联网原住民）
- 当前行为：到店看窗口排队、微信群问"今天有什么"、靠记忆点固定几样
- 痛点：选择疲劳、健康饮食难坚持、对窗口菜品更新不敏感、找不到合口味的新菜

**窗口管理员（WINDOW_MANAGER）**
- 各窗口的运营负责人（窗口师傅 / 店长）
- 技术熟练度中等，习惯 PC 后台
- 当前行为：手动调价、看大致销量、被动接受差评
- 痛点：缺数据决策依据、差评响应慢、促销盲目

### 3.2 Secondary Users（中低频）

**系统管理员（ADMIN）**
- 食堂集团 / 学校后勤的信息化负责人
- 关注全局：用户、食堂、窗口、菜品、订单、评价、积分商城、公告、数据分析

### 3.3 Top 3 User Needs

1. **个性化决策辅助**：基于个人口味、健康目标、上下文（时间/天气/季节）的菜品推荐
2. **闭环的订单体验**：浏览 → 加购 → 下单 → 实时状态 → 评价 → 积分激励
3. **数据驱动的运营洞察**：销量趋势、用户分群、关联推荐、负面评价预警

---

## 4. Solution Overview

### 4.1 Proposed Solution
构建一个**前后端分离的 Web 平台**，把"个性化推荐"与"数据分析"作为两个核心差异化能力嵌入到完整的食堂点餐业务闭环中。

### 4.2 Key Features

**学生侧**
- 多策略个性化推荐（协同过滤 / 内容 / 上下文感知 / 热门，支持融合 + 单策略调用 + 推荐理由）
- 健康目标推荐（高蛋白 / 低脂 / 控碳水 / 控热量）基于历史订单能量与三大供能比
- 菜品浏览、搜索、分类、促销活动
- 购物车 → 下单 → **微信支付 / 支付宝（沙箱）** → SSE 实时订单状态
- 评价（文字 + 图片）与回复
- 积分商城：评价奖励积分 → 兑换餐券
- **微信小程序端**：覆盖学生主流程（浏览、加购、下单、订单状态、评价、积分商城），与 Web 端共用后端 API

**窗口管理员侧**
- 本窗口菜品 / 库存 / 促销 / 套餐管理
- 本窗口订单流转：备餐 → 出餐 → 取餐
- 评价回复、警示处理

**系统管理员侧**
- 数据看板：营收趋势、订单趋势、品类趋势、菜品销量排行、评分排行
- 高级分析：评价 NLP（词云、关键词、菜品特征）、关联规则、用户分群、用户活跃时段、异常检测、对比分析
- 全局资源管理：用户、食堂、窗口、菜品、套餐、促销、券品类、券面、兑换审核、系统公告

### 4.3 Value Proposition

> **"让学生少决策、让食堂多数据"** —— 一套同时给消费者带来"千人千面"个性化体验、给运营方带来"看得见的数据洞察"的高校食堂数字化平台。

差异化亮点：
- **多策略融合推荐引擎**（区别于单一协同过滤）：策略模式 + Redis 缓存 + 推荐理由可解释
- **健康目标驱动推荐**：跳出"猜你喜欢"，真正服务"应该吃什么"
- **完整可演示的业务闭环**：从点餐到积分回收的端到端流程，便于演示和接入真实场景
- **高级数据分析模块**：词云、关联规则、用户分群、异常检测等通常出现在专业 BI 工具中的能力被一并下沉到管理后台

## 5. Business / Project Objectives

> 本项目已通过毕业答辩，现阶段目标已切换为：作为**前端工程师面试作品集**继续打磨，重点强化前端展示、可演示性与工程质量。

### 5.1 Goals (SMART)

1. **作品集化（Portfolio-ready）**：在 2026 年 5 月 23 日前，输出一份可在线演示 / 可截图讲解 / 可现场跑通的版本，能在面试 10 分钟内完整 demo "学生点餐 + 推荐 + 数据看板 + 支付沙箱 + 小程序"全主线。
2. **前端工程质量提升**：在 D2 当天完成至少 3 项可量化改进——Pinia 状态收口（消除 localStorage 双写）、`VITE_API_BASE` 替换硬编码、关键页面拆分大组件、ECharts 组件懒加载。
3. **可解释推荐 UX**：在前端清晰呈现"为什么推荐这道菜"，让推荐引擎的能力对面试官可见、可讨论。
4. **数据分析模块演示化**：数据看板加入 mock 数据集开关，确保任意时刻打开都能看到完整图表，便于现场演示。
5. **多端 + 真实支付**：完成微信支付/支付宝沙箱支付主流程，以及微信小程序学生侧主流程，与 Web 端共用后端 API。

### 5.2 Success Metrics

- 系统可以从零环境 30 分钟内本地启动（含数据初始化）。
- 面试官 demo 全流程零卡顿，关键页面 LCP < 2.5s。
- 至少 3 个前端面试常考点能在本项目中找到对应实践（路由守卫 / 状态管理 / 图表可视化 / 组件封装 / Axios 拦截器 等）。
- README + 开发文档 + 架构图，足以让面试官在不进代码的情况下读懂系统。

### 5.3 Business Value
- 对作者：构建一个可在简历上稳定主推的前端作品集项目，承接前端工程师面试。
- 对潜在落地方：一套可二次开发的高校食堂数字化基线，可向真实校园场景迁移。

## 6. Scope

### 6.1 In Scope（第三轮迭代）
- 前端：Vue 3 + Element Plus + Pinia + vue-router + ECharts 的工程化打磨
- 后端：Spring Boot 3 + Spring Security + JPA + Redis 的接口与服务完善
- 推荐引擎：4 种策略 + 健康目标推荐 + 推荐理由 + 缓存
- 数据分析：评价 NLP / 词云 / 关联规则 / 用户分群 / 异常检测 / 对比分析
- 积分商城：评价奖励 → 积分 → 卡券兑换
- 实时订单 SSE
- 多角色 RBAC（STUDENT / WINDOW_MANAGER / ADMIN）
- Excel 导出（菜品 / 订单 / 评价 / 用户）
- **真实第三方支付集成**（微信支付 / 支付宝 沙箱环境，含签名校验、异步回调、对账查询）
- **移动端小程序**（微信小程序，覆盖学生侧主流程：浏览、加购、下单、订单状态、评价、积分商城）

### 6.2 Out of Scope（明确不做）
- **门店硬件集成**：KDS、叫号屏、打印机、刷脸取餐设备
- **库存供应链**：进货、批次、保质期、财务对账
- iOS / Android 原生应用（仅做微信小程序，不做 React Native / Flutter / 原生）
- 国际化与无障碍适配
- 多租户 SaaS 化与计费

### 6.3 Future Considerations
- 引入 `VITE_API_BASE` 环境变量，支持多环境部署
- 把 `Combo.price` 从 `double` 迁移到 `BigDecimal`
- 用 Flyway/Liquibase 替代 `ddl-auto=update`
- 引入更多推荐算法（如基于深度学习的 Two-tower / Embedding）
- 加入可观测性（Micrometer + Prometheus + Grafana）

## 8. Constraints and Assumptions

### 8.1 Constraints
- 单人开发，主要时间投入在前端打磨与文档输出
- 支付仅接入沙箱 / 测试商户，不处理真实资金
- 不部署到真实校园生产环境（演示导向）
- 不引入超出当前技术栈的新框架（Web 保持 Spring Boot 3 + Vue 3；小程序使用原生微信小程序框架，避免引入额外栈）
- 受限于本机 MySQL / Redis 单实例，不做高可用与水平扩展

### 8.2 Assumptions
- 面试演示在本地或单台云服务器上完成，无需高并发
- 评审者具备阅读 Java + Vue 全栈代码的能力
- 项目结构以 README + `docs/开发文档.md` 为主要外部入口
- 演示数据集（菜品、评价、订单）保持在可控规模（< 10k 量级）

## 11. Risks

- **风险：前端面试官可能更看重 React 生态**
  - 可能性：Medium
  - 缓解：在 README 中明确"项目以 Vue 3 体现工程能力"，并准备 Vue↔React 的对照讲解；必要时可基于本项目衍生一个 React 版本的子页面作为补充。

- **风险：项目体量过大，面试讲不完导致重点散乱**
  - 可能性：High
  - 缓解：提前准备 3 条"5 分钟主线"演示脚本（点餐闭环 / 推荐引擎 / 数据看板），允许面试官按兴趣选讲。

- **风险：演示环境（MySQL / Redis）启动失败影响 demo**
  - 可能性：Medium
  - 缓解：提供 docker-compose 一键启动脚本；准备本地录屏作为兜底。

- **风险：`baseURL` 硬编码 / Pinia-localStorage 双写等历史债拖累代码质量印象**
  - 可能性：High
  - 缓解：在 M4 里程碑前修复，作为"重构能力"的展示点写进 README。

- **风险：演示数据不够丰富，数据分析图表空旷**
  - 可能性：Medium
  - 缓解：M5 输出 mock 数据集与"演示模式开关"。

- **风险：后端 `ddl-auto=update` 与生产规范背离，可能被面试官追问**
  - 可能性：Low–Medium
  - 缓解：在文档中显式说明"开发期使用，生产建议改为 validate + Flyway/Liquibase"，化被动为主动。

- **风险：支付沙箱联调失败 / 商户号申请不到位，影响支付主线演示**
  - 可能性：Medium
  - 缓解：优先使用微信支付/支付宝官方沙箱；如商户资质受限，则以 H5/扫码沙箱 + 内置 Mock 双轨实现，演示开关切换；保留现有模拟回调接口作为兜底。

- **风险：微信小程序与 Vue Web 端共用后端，CORS / 域名 / token 校验易出兼容问题**
  - 可能性：Medium
  - 缓解：小程序端走 `wx.request` 走业务域名白名单；后端鉴权统一通过 JWT，避免 Cookie/Session；小程序登录态用同一 `Authorization: Bearer` 头。

- **风险：1 周内同时交付 Web 打磨 + 支付 + 小程序节奏极紧**
  - 可能性：High
  - 缓解：D1 一次性产出 PRD + 架构 + 故事拆分，避免文档与代码交错返工；M5 支付层与 M6 小程序网络层共用同一套 JWT 鉴权和 API，降低重复成本；准备"Mock 支付兜底开关"，若沙箱联调当天受阻可秒切 mock 继续推进，不阻塞后续里程碑。
